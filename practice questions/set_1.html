The Reference Number
A timeout after a side-effect has already executed is the classic double-effect race — and the fix is an idempotency key, not tuning.
Without a key
send payment➤server executes ✓➤client times out ✗➤retry → 💥 paid twice
With an idempotency key
send + 🔑 key➤server executes ✓➤times out ✗➤retry, SAME key → “already done — here’s the original result” ✓
Failure provably BEFORE executionconnection refused · validation — nothing ran, retry now
Timeout AFTER dispatch = unknown statelook up the effect by key — never replay it
The UPI moment: the machine says “failed”, you show the reference number — the merchant finds the original transaction and nobody pays twice. Longer timeouts and fewer retries only make the accident rarer; the mechanism stays armed.

Gates By Reversibility
Gates are expensive queue-time — they belong exactly where stakes and rules point, and nowhere else.

Question 13 · Unsupportable Commitments & SLAs concept only — no answer inside
Promise The Train, Not The Traffic
A probabilistic system has a distribution, not a destiny — honest commitments are populations and percentiles.
✖ Promise the traffic
“100% perfect · every single time · flat cost”

Per-response perfection on a system with variance — a promise about traffic you don’t control. The five-minutes-away friend.

✓ Promise the train
95% in the window

A percentile turnaround · sampled accuracy on a population · the correctness-critical slice routed to humans under its own SLA.

The honest train answer: “forty to fifty minutes, and here’s the peak-hour pattern.” Same journey, same person — one is a statistic you own; the other is a lie about traffic you don’t.
🏷 The one rule: populations and percentiles, never per-response perfection — capacity buys headroom, not certainty.
